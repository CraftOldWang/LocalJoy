## 1. 正常下单：各组件分别负责什么

```text
用户抢购
  → Redis Lua：检查活动时间、库存、购买资格，预扣库存并记录订单归属
  → 同步向 RocketMQ 发送建单消息，获得发送结果
  → 接口返回订单 ID，表示请求已受理
  → 消费者：在 MySQL 事务中扣库存、创建待支付订单
  → 发送关单延迟消息
  → 用户确认支付，或者到期后取消订单并返还库存
```

“异步下单”指数据库建单由消费者执行。入口仍同步等待 MQ 发送结果，不是整个请求都不等待。返回订单 ID 也不等于数据库订单已经生成。

| 组件或记录 | 负责的问题 |
| --- | --- |
| Redis 秒杀库存 | 快速判断还能放进多少个购买请求，减少数据库入口压力 |
| Redis 预占记录 | 记录某个用户当前占用的库存属于哪个订单 |
| RocketMQ | 将已受理请求交给消费者，缓冲数据库入库流量；失败消费可重试 |
| MySQL 库存与订单 | 在事务中完成落库校验、扣减、订单状态变更 |
| 延迟消息 | 到达后触发一次超时检查，具体能否关单由数据库条件决定 |

Redis 和 MySQL 并不是各卖出一件商品：它们分别记录入口预占与落库结果，处理过程中可以暂时不同步，失败时需要协调恢复。

### 三个常用术语

- **幂等**：同一个业务动作执行多次，业务结果与成功执行一次相同。它不要求每次都不做任何操作。
- **补偿**：撤销前面已经完成、后来又需要取消的业务变更，例如返还已预扣的库存。
- **预占归属**：不仅知道“用户买过”，还知道“当前是哪一笔订单占着库存”。

## 2. 重复补偿：同一份库存不能返还两次

### 问题怎样发生

Redis 已经预扣，但数据库创建订单失败，需要把 Redis 库存加回来。如果消息被重复消费，而每次失败都直接执行 `INCR`，就会出现：

```text
初始库存 1 → A 预扣后 0 → 第一次补偿后 1 → 第二次补偿后 2
```

第二次补偿凭空增加了可售库存，后续可能放入超出实际库存的请求。

### 当前怎样保护

每个商品都有用户到订单的映射，例如 `用户 U → 订单 A`。回滚脚本先检查当前归属：

```text
当前预占订单 != 本次要补偿的订单 → 什么都不改
当前预占订单 == 本次要补偿的订单 → 库存加一，删除或替换预占记录
```

普通取消时删除记录。第一次补偿后，A 已经不再持有预占，第二次回滚自然不会再加库存。检查、加库存、删除或替换记录都在同一个 Lua 脚本中，避免并发请求同时通过检查。

有一个特殊分支：如果数据库发现该用户已有有效订单，需要释放本次无效预占，同时把购买记录恢复为已有有效订单的 ID，不能顺便放开这个用户的购买资格。

**Redis Lua 的原子性只覆盖脚本内的 Redis 操作，不覆盖 Redis、MQ、MySQL 三个系统。**

代码：[product_reservation_rollback.lua](../src/main/resources/product_reservation_rollback.lua)。

## 3. 迟到消息：旧订单不能干扰新订单

### A 已取消，用户又下了 B

| 顺序 | 发生的事情 | 当前预占归属 | 正确行为 |
| --- | --- | --- | --- |
| ① | 用户 U 创建订单 A | U → A | A 占用库存 |
| ② | A 取消并完成回补 | 无 | 允许重新购买 |
| ③ | 同一个用户创建订单 B | U → B | B 占用库存 |
| ④ | A 的旧补偿消息再次到达 | U → B | 不加库存，不删除 B 的记录 |

如果只按照用户 ID 删除购买记录，第四步就可能把 B 的预占释放掉。**因此，用户相同不代表是同一次业务操作。**

当前有两处归属检查：

1. 消费者准备创建尚不存在的订单 A 时，检查 Redis 预占是否仍属于 A；如果属于 B 或已经不存在，就不创建 A。
2. 回滚 A 的预占时，再比较当前订单 ID；如果属于 B，就不执行补偿。

数据库中已经存在的 A 也有独立订单 ID 和状态。重放它的消息不能把已经取消的 A 当成新单再扣一次库存。

### 为什么发送超时也会产生迟到消息

```text
生产者发送 A → Broker 可能已收到 → 确认响应丢失 → 生产者报告超时
```

发送超时不能证明消息没到 Broker。当前入口与消费者使用同一把“商品 + 用户”锁：入口持锁完成发送结果处理及失败回滚，消费者取得锁后再判断预占归属。如果 A 已被撤销，之后到达的 A 消息不能重新创建订单。

这处理的是当前协议中的发送结果不确定与迟到消费，**没有覆盖所有进程崩溃或 Redis 故障情形**，见第 9 节。

代码：[ProductOrderServiceImpl](../src/main/java/com/hmdp/service/impl/ProductOrderServiceImpl.java)，重点阅读 `seckillProduct`、`createProductOrder`、`rollbackReservation`。

## 4. 消费幂等：已完成的不重复，未完成的继续做

### 订单已落库，后续延迟消息却没发出去

```text
扣 MySQL 库存、创建订单 → 数据库事务提交成功
发送超时关单消息       → 失败
原来的建单消息         → 被重新消费
```

此时有两种错误处理：重新扣库存会多扣；一看到订单存在就直接结束，可能漏掉后续关单检查。

当前按照订单 ID 判断进度：

| 订单情况 | 消费者处理 |
| --- | --- |
| 尚不存在 | 校验预占，再通过事务扣库存并建单 |
| 已存在且待支付 | 不重复扣库存，继续尝试发送延迟消息 |
| 已存在且已取消 | 根据取消原因进行幂等的预占回补 |
| 已存在且已支付 | 不再创建订单或扣减库存 |

被数据库拒绝的尝试也会保存为取消订单并记录原因，避免每次重试都把它当作全新的请求。

延迟消息可能因此重复发送，但关单入口也会校验状态、版本、截止时间，所以消息重复不应造成业务效果重复。

**这里不依赖“消息绝不重复”，而是让重复到达可以安全处理。**

## 5. 重复支付确认：状态只变更一次

### 典型场景

第一次确认已经将订单改为已支付，但响应丢失，客户端再次请求。如果第二次直接报“状态不对”，调用方就难以区分“上一次已经成功”和“支付没有成功”。

当前处理顺序：

1. 检查订单存在且属于当前登录用户。
2. 如果已支付，直接返回成功，不再修改版本与支付时间。
3. 如果待支付且未过期，执行带状态、版本和截止时间条件的更新。
4. 如果并发更新失败，使用 `FOR UPDATE` 重新读取当前记录；若另一确认请求已经成功，也返回成功。
5. 已取消、已超时等其他情况返回失败。

两个并发确认请求不能各自使版本号增加一次；第二个请求可以确认已有结果。

### 当前“支付”的准确范围

本节描述的是**本地模拟确认**路径。2026-09-16 新增支付宝沙箱路径：支付流水、RSA2 验签、金额与商家核对、重复通知处理、服务端查单恢复均已实现；配置和独立测试证据见[支付宝沙箱接入与支付一致性](alipay-sandbox.md)。沙箱不会扣真实资金。

沙箱通知晚到时，先以渠道事实核对订单；超时取消前先确认渠道关闭，不能只按本地时钟释放库存。若已经出现冲突终态，保留人工核账记录；自动退款仍未实现。下节的截止时间条件适用于本地模拟确认，验签后的渠道成功通知有独立处理逻辑。

代码：[ProductOrderServiceImpl.payOrder](../src/main/java/com/hmdp/service/impl/ProductOrderServiceImpl.java)。

## 6. 支付与关单：条件更新决定谁能成功

### 先查询再无条件更新为什么危险

```text
支付线程：查到待支付
关单线程：也查到待支付
支付线程：改为已支付
关单线程：覆盖成已取消，并返还库存
```

查询只说明“读取时是什么状态”，不能保证“更新时仍是这个状态”。

### 状态、版本、截止时间一起检查

以下为说明用的 SQL，字段值用文字简化；实际实现使用 MyBatis-Plus 条件更新：

```sql
-- 支付确认
UPDATE 订单
SET 状态 = 已支付, version = version + 1
WHERE id = ? AND 状态 = 待支付
  AND version = 读取时版本
  AND 截止时间 > 本次检查时间;

-- 超时关单
UPDATE 订单
SET 状态 = 已取消, version = version + 1
WHERE id = ? AND 状态 = 待支付
  AND version = 读取时版本
  AND 截止时间 <= 本次检查时间;
```

应用将当前时间作为条件参数传入。执行成功以数据库实际更新行数为准。一方成功变更状态与版本后，另一方拿着旧版本就不能覆盖结果。

状态和版本限制允许的状态迁移，截止时间限制业务上的可支付窗口。分布式锁用于协调部分流程，数据库条件更新仍是支付与关单竞争的关键保护。

### 三类关单保护

| 情况 | 当前处理 | 避免的问题 |
| --- | --- | --- |
| 延迟消息提前到达，订单尚未到期 | 不关单，重新安排延迟检查 | 不能把“消息到了”当作“订单一定到期” |
| 同一订单收到多次关单请求 | 只有从待支付成功改为取消的事务才返还数据库库存 | 数据库库存重复增加 |
| 数据库关单成功，Redis 回补失败 | 消费失败触发重试；重试只补 Redis 步骤 | 漏补 Redis 或再次回补数据库 |

**订单取消与 MySQL 库存返还在同一个数据库事务中。** 库存返还失败会使该事务回滚，避免数据库内部出现“订单已取消、库存没有恢复”的半完成结果。

Redis 回补在数据库事务之外，通过失败重试和预占归属校验完成。已经支付的订单不会被此超时逻辑关闭。

代码：[ProductOrderServiceImpl.cancelOrder](../src/main/java/com/hmdp/service/impl/ProductOrderServiceImpl.java)。

## 7. Canal 与 MQ：商品缓存如何跟上数据库

### 缓存的内容与查询流程

新增 `GET /product/{id}` 缓存商品标题、价格等 `tb_product` 元数据。**详情缓存不负责秒杀库存判断，商品列表也尚未缓存。**

```text
读取 Redis
  ├─ 命中：返回缓存
  └─ 未命中：取得商品锁 → 再查一次缓存 → 查询 MySQL → 写入缓存
```

正常商品缓存 300 秒；不存在的商品缓存空值 30 秒，减少反复查询不存在的 ID。取得锁后再次查询，是因为前一个线程可能已经完成重建。

锁最多等待 500 ms；取不到锁会直接查询数据库，但不写缓存。因此是有界等待与减少重复回源，不是任何负载下都只允许一个数据库查询。

### Canal → MQ → 删除缓存

Canal 读取 MySQL binlog 中的数据库变更。商品资料修改后的处理链路为：

```text
MySQL 修改商品并提交
  → binlog 记录变化
  → Canal 解析商品表变更事件
  → RocketMQ 传递事件
  → 应用消费者按商品 ID 删除 Redis 缓存
  → 下一次查询从 MySQL 获取当前资料并重新缓存
```

因此，绕过 Java 接口直接执行 SQL 修改商品，也能触发缓存失效。消费者限定目标数据库，并处理商品表的插入、更新、删除事件。

### 为什么删除，不直接把事件里的值写回缓存

假设商品先改成版本 2，再改成版本 3。如果旧事件迟到并直接写值，可能把缓存从版本 3 覆盖回版本 2。

删除事件重复或迟到，主要代价是多一次缓存未命中；后续重建仍从数据库取当前值。删除重建避免了依赖消息值更新缓存时的版本倒退问题，但仍有消息传播造成的陈旧窗口。

### 已经删了缓存，旧值为什么还能回来

| 顺序 | 查询线程 | 更新及失效链路 |
| --- | --- | --- |
| ① | 缓存未命中，读到数据库旧值，尚未写回 | |
| ② | 暂停 | 数据库更新并提交 |
| ③ | 暂停 | 消费变更事件，删除缓存 |
| ④ | 将先前读到的旧值写入缓存 | 删除已经结束 |

当前让**缓存重建与缓存删除共用同一把商品锁**。旧值回填持锁时，失效处理等待；回填完成后再删除，从而避免上述先删除、后回填旧值的顺序。

失效处理等待锁 1 秒仍失败，或者 Redis 删除报错，都会抛出异常，让 MQ 重试，不能捕获异常后仍把消息当作处理成功。

### 为什么仍然叫最终一致性

数据库提交到变更事件处理完成之间，读请求仍可能命中旧缓存。MQ 重试与 TTL 提供恢复路径，不等于实时同步，也不等于永久故障下无条件保证一致。

重试超过上限需要处理死信消息；当前未新增完整的死信告警与自动重放平台。分布式锁失效和 Redis 主从切换也未在本轮验证。

代码：[ProductCache](../src/main/java/com/hmdp/utils/ProductCache.java) · [ProductCanalCacheHandler](../src/main/java/com/hmdp/canal/ProductCanalCacheHandler.java) · [CanalFlatMessageConsumer](../src/main/java/com/hmdp/canal/CanalFlatMessageConsumer.java)。

## 8. Lua校验、数据库约束与滑动窗口限流

### Lua 与数据库各自防什么

| 保护 | 具体作用 |
| --- | --- |
| Redis Lua 活动时间校验 | 未开始、已结束、缺少活动元数据时拒绝抢购；使用 Redis 服务端时间 |
| Redis Lua 原子预扣 | 库存判断、购买资格检查、扣减和写入预占归属一起执行 |
| MySQL `stock > 0` 条件扣减 | 数据库落库不能把库存减为负数 |
| 订单主键 | 同一订单 ID 不能重复创建 |
| 有效用户生成列 + 唯一索引 | 同一商品、同一用户不能有多个未取消订单；已取消记录不占该唯一资格 |

当前“一人一单”允许取消后重新购买，已支付订单仍占购买资格；不是“一生只能发起一次请求”。

代码：[商品秒杀 Lua](../src/main/resources/product_seckill.lua) · [V4 数据库迁移](../src/main/resources/db/migration/V4__product_order_deadline_and_unique_buyer.sql)。

### 滑动窗口怎样计算

每次访问执行一个 Lua 脚本：读取 Redis 当前时间，移除窗口之外的访问记录，统计剩余数量，未超过限额就加入本次唯一访问记录并设置过期时间。ZSet 分数为时间，成员使用唯一请求标识，避免同一毫秒的请求相互覆盖。

全局、IP、用户使用不同维度的 Key。当前商品秒杀注解按单商品限制：全局每秒 1000、单 IP 每秒 50、单用户每秒 5。

不再直接相信客户端填入的 `X-Forwarded-For` 或 `X-Real-IP`，避免请求者伪造地址来更换限流身份。当前使用 `getRemoteAddr()`；经过本地代理时来源地址会合并，正式部署需要明确可信代理及真实地址配置。

多个维度依次检查；后续维度拒绝时，前面已计入的访问不会回滚。这是保守计数，并非所有维度一起成功或一起失败。

代码：[RateLimitAspect](../src/main/java/com/hmdp/aspect/RateLimitAspect.java) · [滑动窗口 Lua](../src/main/resources/rate_limit_sliding_window.lua)。

## 9. 测试证据与尚未解决的边界

### 已有验证

以下引用 2026-09-14 已保存的运行记录；本文整理不代表又执行了一轮测试。

| 场景 | 验证内容 |
| --- | --- |
| 并发抢购与重复消费 | 30 份库存、200 次申请，受理 30 单；每单重复投递后不重复扣库存 |
| 发送结果不确定与迟到消息 | 模拟确认丢失；撤销 A、创建 B 后，A 的旧消息不能干扰 B |
| 重复补偿 | 数据库拒绝同一订单，反复消费只回补一次 |
| 事务提交后延迟消息发送失败 | 原消息重试能补发延迟消息，不再次扣库存 |
| 重复关单与重买 | A 关闭后重买 B，重放 A 的消息不撤销 B |
| 支付与关单 | 检查订单归属；截止时间前后分别并发确认和关单，状态与库存符合预期 |
| 缓存旧值回填 | 用线程同步点暂停旧值读取，再更新数据库和触发失效，验证最终删除旧缓存 |
| Canal 消费异常 | 可控异常向上传播，以便 MQ 重试；忽略其他数据库事件 |
| 真实 RocketMQ | 实际 Broker 重投、延迟投递与关单通过 |
| 真实 Canal 链路 | 直接 SQL 更新临时商品，观察已有缓存被删除、HTTP 重读得到新值 |

常规测试使用真实 MySQL、Redis，但用模拟 MQ 注入发送故障；真实 MQ 与 Canal 链路另行运行。支付并发用例没有穷举截止时间边界的全部线程交错，也没有验证真实渠道扣款。

### React 联调新增的首次消费保护（2026-09-16）

“MQ 已受理”与“消费者已经处理”是两件事。新 Topic 的首条消息可能先于消费者首次分配队列到达；默认从末尾开始时，新组可能直接跳过它。商品建单与商品关单消费者现明确使用 `CONSUME_FROM_FIRST_OFFSET`，让没有保存位点的新组从最早可用消息开始。已有位点继续有效，不能靠重启恢复历史遗漏。

真实 MQ 回归先发消息，再启动两个新组，复用两个消费者的实际生命周期配置，验证均收到这条消息。历史消息恢复前要核对订单、Redis 预占归属和消息身份；本次旧演示消息最终通过单条重发恢复，原有幂等机制仍负责防止重复扣库存。详见[React 验收记录](frontend-acceptance.md)。

### 仍然不能宣称已经解决的事情

1. **预占后的崩溃窗口**：应用在 Redis 预占成功、MQ 发送前退出，仍可能留下孤立预占。当前没有完整的持久化待发送记录或预占对账任务，不能说整条链路绝对不丢单。
2. **生产支付闭环**：已接支付宝沙箱，验签、幂等与查单有独立测试；生产支付、自动退款和管理核账尚未实现。实网扫码与公网回调的验证状态见支付指南，不能将沙箱测试描述成生产资金经验。
3. **永久故障与基础设施切换**：Redis 数据丢失、锁失效、主从切换和长时间死信堆积未完成验收。
4. **容量与收益数字**：短批次服务层测量不能证明 HTTP 峰值 TPS 2000，也未测得缓存降低查询延迟 30%。具体范围见[下午复测报告](evidence/retest-2026-09-14-162241/README.md)。

## 10. 面试时可以怎样串起来讲

> 我在商品秒杀入口用 Redis Lua 校验活动时间、库存和购买资格，并记录用户到订单 ID 的预占关系。请求发到 RocketMQ 后，由消费者在数据库事务中扣库存和创建订单，数据库条件扣减与唯一约束负责落库兜底。
>
> 我重点处理了重复消息和部分失败：已经完成的扣库存不重复，延迟消息发送失败可以重试补发；回补时必须匹配当前预占的订单 ID，所以旧订单的消息不能释放后来新订单的库存。
>
> 超时关单与模拟支付确认都通过状态、版本和截止时间进行条件更新。数据库关单与库存返还在一个事务中，Redis 回补失败再通过重试恢复。商品详情缓存则通过 Canal 订阅数据库变更，经 MQ 删除缓存，重建和失效共用商品锁，避免旧值在删除后回填。
>
> 这些场景做了并发、故障注入和真实中间件验证；另外接入了支付宝沙箱，补充支付流水与查单恢复。生产资金、自动退款以及秒杀预占后进程崩溃的对账恢复仍是待补齐部分。

记忆要点：**订单 ID 管预占归属；状态、版本和截止时间管订单变更；Canal、消息重试和 TTL 管缓存收敛。**
