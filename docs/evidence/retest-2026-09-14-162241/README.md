# 2026-09-14 下午性能复测

时间：16:22–16:25。用户补充午间开启了省电模式，因此在当前状态按相同代码和负载连续复测三次。开始与结束时 `powercfg /getactivescheme` 均显示“平衡”；午间没有独立记录电源状态，当前读数也不能完整代表 Windows 或厂商工具的节能设置，因此这里只比较实测结果，不把变化全部归因于电源模式。

## 参数与成功口径

- 每次订单测量：16 并发、200 个不同用户、200 份库存，服务层 → 真实 RocketMQ → MySQL；不含 HTTP、AOP 限流。
- 每次缓存测量：先预热 100 次，三轮交替查询，每轮缓存 / MySQL 各 500 次；单线程、同一个商品、不含 HTTP。
- 三次运行均通过两个测试，实际 Broker 重投与延迟关单也通过。测量批次合计 600 单受理、600 单落库。
- 未修改业务代码、限流配置或测试参数来提高结果。使用独立数据库、Redis DB 14 和测试 Topic。

## 结果

| 测量 | MQ 受理（单/秒） | 全部落库（单/秒） | 缓存均值（ms） | MySQL 均值（ms） | 缓存均值降低 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 午间记录 | 531.90 | 76.87 | 1.151 | 1.163 | 0.99% |
| 下午第 1 次 | 910.47 | 127.37 | 0.935 | 0.956 | 2.27% |
| 下午第 2 次 | 802.58 | 121.85 | 0.997 | 1.014 | 1.64% |
| 下午第 3 次 | 787.70 | 123.85 | 1.021 | 1.006 | -1.56% |
| 下午三次合并 | **830.14** | **124.32** | **0.984** | **0.992** | **0.76%** |

订单合并吞吐按总成功订单数除以各批次对应阶段耗时之和计算，不是简单平均 TPS。缓存样本数相同，按全部样本的平均延迟比较。

相对午间，合并受理吞吐提高约 **56%**，合并落库吞吐提高约 **62%**。当前状态确实明显更快；午间的小批量结果不应被当成系统容量上限。缓存与数据库都变快了，但两条路径之间仍只有很小差距，第三次缓存略慢。

这些依然是 200 单的短批次测量，不能推断持续负载下的峰值容量，也不能与未知配置、接口和成功口径下的“TPS 2000”直接等同。当前缓存对照没有出现降低 30% 的结果。
