审查日期：2026-09-14。范围为 **商品秒杀链路**，原版优惠券链路保留，不能将本轮商品测试结论直接套到优惠券接口。

## 关键实现位置

- `src/main/resources/product_seckill.lua`：原子校验、预扣、预占归属。
- `src/main/resources/product_reservation_rollback.lua`：只有当前订单拥有预占时才回补；迟到消息不能取消后来重下的订单。
- `ProductOrderServiceImpl`：同步发送 MQ 后返回受理结果，消费者异步落库；主键幂等、数据库事务、延迟消息重发、支付 / 关单 CAS。
- `V4__product_order_deadline_and_unique_buyer.sql`：`expire_time`，生成列加唯一索引保证同一商品同一用户仅一个有效订单。关闭后允许重新下单。
- `ProductCache` / `ProductCanalCacheHandler`：缓存商品元数据，不把展示缓存当成秒杀库存；失效与重建使用同一个 Redisson 锁。
- `RateLimitAspect` / `rate_limit_sliding_window.lua`：全局、IP、用户维度，拒绝请求由现有异常处理器返回 HTTP 429。

## 验证与复现

在仓库根目录使用 JDK 8：

```powershell
.\scripts\test-resume.ps1 -JavaHome '你的 JDK 8 目录'
.\scripts\test-resume.ps1 -JavaHome '你的 JDK 8 目录' -RealMq -Benchmark
.\scripts\test-product-canal.ps1
```

脚本准备独立的 `hmdp_resume_test` 数据库，测试配置使用 Redis DB 14。不要将这个 profile 指向生产数据。测试只删除自己创建的商品及订单，不执行 FLUSHDB 或清空演示库。

Canal 冒烟脚本需最新后端运行在 8081，且本项目 Canal 容器已加载商品表订阅；它在本地演示库 `hmdp` 创建一条随机标记的临时商品、直接 SQL 更新、检查缓存失效与重新查询，最后只删除该临时商品。

默认测试使用真实 MySQL / Redis，模拟 MQ 发送以注入确认丢失、延迟消息发送失败等故障。`-RealMq` 另建独立测试 Topic / 消费组，验证 Broker 的实际重投及延迟投递。测试 Topic 按时间戳命名，消息按 Broker 保留策略清理，不使用业务 Topic 压测。

`-Benchmark` 输出 `target/resume-cache-benchmark.json`；`-RealMq` 输出 `target/resume-mq-evidence.json`。缓存对照是同一个商品的预热后服务层查询与直接 MySQL 查询，交替执行三轮，不含 HTTP。订单测量区分 MQ 已受理和数据库已落库，不能把限流拒绝或库存不足响应计入成功订单 TPS。

## 首次测量记录（14:43–14:48）

环境：Windows，AMD Ryzen 9 7940HX（16 核 / 32 线程），JDK 8u342；Docker MySQL 5.7、Redis 6.2、RocketMQ 5.3.2，机器同时运行其他服务。不是独占机器的容量压测。

商品缓存：预热 100 次，每条路径每轮 500 次，交替查询共三轮；缓存平均 1.151 ms，数据库平均 1.163 ms，约降低 0.99%。差距很小，且第一轮缓存更慢，不能宣称降低 30%。收益更应通过减少数据库请求量、高并发负载下的数据库压力来继续验证，而不是人为给数据库增加延迟。原始结果见 [缓存对照记录](evidence/2026-09-14-cache-benchmark.json)。

订单：16 并发、200 个不同用户、200 份库存，经服务层调用、真实 RocketMQ、异步消费者写入 MySQL；200 单全部受理并落库。受理阶段 0.376 秒，约 531.90 单/秒；从发起至全部落库 2.602 秒，约 76.87 单/秒。它是小批量端到端冒烟测量，不含 HTTP、AOP 限流，也不是稳定负载下的峰值容量，不能据此填写 TPS 2000。原始结果见 [MQ 记录](evidence/2026-09-14-mq-evidence.json)。

测试结果：14 个真实 Redis / MySQL 的功能及可控故障用例通过；缓存测量用例通过。真实 MQ 用例首次等待重投 / 延迟链路超时，调整为先创建 Topic 再启动消费者后单独重跑通过，已观察实际 Broker 重投和延迟关单。不是通过手动调用两次消费者来代替真实 MQ 验证。

最终常规回归：16 个已发现用例中 14 个通过、0 失败 / 错误，2 个需显式开关的 MQ / 测量用例跳过；它们的独立运行结果记录在上文。详见 [功能用例清单](evidence/2026-09-14-functional-tests.json)。

实际 Canal 冒烟也通过：绕过 Java 直接更新 MySQL 测试商品，观察到已有缓存被删除，HTTP 重读得到新值；验证路径为 MySQL → Canal → RocketMQ → 商品缓存处理器。观察时间 737 ms 包含 Docker CLI 与轮询耗时，不作为传播延迟基准。临时商品已清理，见 [Canal 记录](evidence/2026-09-14-canal-evidence.json)。

## 电源状态变化后的复测（16:22–16:25）

用户补充午间开启了省电模式。下午按原代码和参数连续复测三次，测量批次共 600 单全部受理并落库：合并受理约 **830 单/秒**，全部落库约 **124 单/秒**，相对午间分别提高约 **56% / 62%**。原结果不应作为系统容量上限。

缓存与 MySQL 查询均加快，合并均值分别为 **0.984 / 0.992 ms**，相对差异约 **0.76%**。复测始末系统电源方案均显示“平衡”，但不是只改变电源模式的受控实验。仍保留短批次、服务层测量的范围，不据此断言系统最大 TPS，也没有测到缓存降低 30%。三轮数据和环境记录见 [下午复测报告](evidence/retest-2026-09-14-162241/README.md)。

## 必须保留的边界

1. **支付是本地模拟确认**，没有接第三方支付平台或验签回调。简历宜写“支付确认与关单竞争”，不能写成已验收真实支付回调。
2. 新商品在数据库提交后才初始化 Redis 活动元数据。历史商品只存在库存 Key 的，需要先核对库存、订单和未完成消息，再准备活动元数据；不要覆盖正在售卖的 Redis 库存。
3. 如果应用恰好在 Redis 预占后、MQ 发送前崩溃，仍可能留下孤立预占；当前没有持久化发件箱或预占对账任务。Redis 自身丢数据、锁失效或主从切换也不在本轮验证范围。数据库条件扣减和唯一约束仍是落库兜底，不能声称整条链路“绝对不丢单”。
4. 商品缓存采用删除重建，允许变更传播期间短暂读取旧值。MQ 重试是有限的，超过上限进入死信队列，需要告警和人工重放；正值缓存 300 秒、空值缓存 30 秒的 TTL 提供额外收敛路径。不能把“最终一致性”写成任何永久故障下的无条件保证。
5. 商品详情缓存只包含 `tb_product` 元数据；库存与活动数据由列表查询和秒杀链路提供。商品列表暂不缓存，避免把两种测量混在一起。
6. 当前商品秒杀注解限制单商品全局每秒 1000、单 IP 每秒 50、单用户每秒 5。单 IP HTTP 压测不应通过伪造转发头绕过限制；服务层测量也不能作为该 HTTP 接口 TPS 的证明。经反向代理部署时，需要由可信代理配置真实客户端地址；本地代理请求的 IP 维度会合并。
7. 多个限流维度按顺序检查，后续维度拒绝时，已通过的维度仍计数，属于保守准入；不是所有维度一起提交或一起回滚。

## 可采用的简历表述

项目描述：面向本地生活场景的学习项目，围绕店铺商品、秒杀订单和内容笔记，实现 Redis 库存预扣、RocketMQ 异步下单、商品热点缓存、超时关单和多维接口限流。

- 使用 Redis + Lua 原子完成秒杀库存预扣和一人一单校验，结合数据库条件扣减与有效订单唯一约束防止重复落库及超卖。
- 使用 RocketMQ 异步处理商品订单，通过订单 ID、预占归属和幂等补偿处理重复消息及部分失败场景。
- 基于 RocketMQ 延迟消息实现超时关单，使用截止时间与状态 / 版本条件更新协调模拟支付确认和关单，并支持重复回补保护。
- 实现商品详情缓存与互斥重建，订阅 Canal 商品表变更，经 RocketMQ 消费执行缓存失效；通过重试与 TTL 控制缓存陈旧窗口。
- 基于 Redis ZSet、Lua、AOP 和注解实现滑动窗口限流，支持全局、IP、用户维度。

性能数字暂不放入上述版本；只有能解释数据集、成功口径、并发度、环境和测试范围时才补入。
